# Simple Doc

按用户指定的目标路径或范围清理文档与注释里的历史层积，例如 `auto-data-evolution/`、`README.md` 或所有配置注释。

## 这个 skill 在解决什么

文档和注释会随时间长出第二层内容：不是"这东西怎么用"，而是"我们当初怎么弄错的"。
写的时候它有用——刚踩完坑，怕别人再踩。但读者是来找**怎么做**的，事故叙事让他
每次都要先读一遍别人的过去，再自己反推出结论。

清理的目标不是删信息量,是**把结论从叙事里取出来,扔掉叙事**。

---

## 0. 先看项目级约束——它优先于本 skill

动手之前,读一遍项目自己的说明:`CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING.md`、
`docs/` 下的写作约定、`.cursorrules`。**只要项目对文档或注释有自己的规定,
以项目的为准**,本 skill 的规则退到它后面。

有些项目是**有意**把事故记在注释里的,常见表述:

> "Module docstrings carry the reasoning and the incident that produced each rule.
> They are the design record."
>
> "Commit messages are a sentence about what was learned, not a change summary."

这类项目里,那些叙事不是包袱,是被当作设计依据在维护的资产。照本 skill 清掉,
等于删掉项目刻意保存的东西。

**遇到冲突时:**

1. **停下,先说明冲突**,把项目原文引给用户,不要自行决定哪边对。
2. 给出两个选项,让用户选:
   - 按项目约束办 —— 缩小清理范围,把受约束的文件类别整个排除;
   - 一并修订项目约束 —— 用户同意后,**先改 `CLAUDE.md` 等说明,再清理**。
     顺序不能反:说明不改,下一个 session 会照着它把叙事重新写回去,清理白做。
3. 用户明确表态后按其决定执行,不再重复劝说。

**范围没有覆盖到的文件不算冲突。** 若约束只针对 docstring,而这次只清 README 和
配置注释,直接做,做完提一句"docstring 未动,因为 CLAUDE.md 要求保留"即可。

## 三条规则

### 1. 纯历史 → 删,仿佛从没发生

约束不了任何当下行为的记录:某年某月谁改错了什么、曾经用过的旧值、"本来是 A
后来改成 B"的过程。删干净,不留"(历史原因)"这类残迹。

### 2. 试错过程 → 只留最优解

setup / 排查类文档常记着"我先试了 A,不行;又试了 B,也不行;最后 C 成了"。
**只留 C**,连同 C 之所以是 C 的那句机制。A 和 B 一起删。

### 3. 仍然有效的经验 → 保留结论,改写成正向指令

这是唯一需要动脑的一条。判断标准:**去掉这句话,读者会不会把代码改回错的样子、
或者走回错的路?** 会,就留;不会,按规则 1 删。

留下来的必须改写:

| 删掉 | 换成 |
|---|---|
| 不要做 X,否则会 Y | 要做 Z |
| 曾经因为 X 导致 Y | (机制的一句陈述) |
| ⚠️ 小心 X | (把正确做法写进步骤里) |

## 判断流程

对每一段历史/告诫,依次问:

```
1. 它约束现在的代码或流程吗?
   否 → 删(规则 1)
   是 ↓
2. 去掉它,读者会退回错误做法吗?
   否 → 删(规则 1)
   是 ↓
3. 改写成正向指令 + 机制(规则 3)
```

第 2 步容易高估。**如果代码结构本身已经堵死了那条路**(加了断言、改了类型、
路径变成了唯一入口),那这段告诫已经由代码承担了,文字是冗余的 → 删。

## 改写的手艺

### 保留"机制",丢掉"事故"

机制是关于世界如何运作的持久事实,事故是一次性的。

```diff
- # 2026-08-15 那台机器的盘坏了,kubectl、kubelogin 和 kubeconfig 一起没了,
- # 我按 ARM 可见性去找集群,找到一个名字对得上的 t2vginfra,方向整个偏了。
- # 正确的问法不是"哪个集群我在 Azure 上看得见"。
+ # AAD 集成的 AKS 由 Kubernetes 自己的 RBAC 授权,与 ARM 资源可见性无关:
+ # `az aks list` 看不到的集群,`kubectl` 也可能正常。按 namespace 认集群。
```

"AAD 授权归 RBAC 管"是机制,明年依然成立;"我找错了 t2vginfra"是事故。

### 把告诫折进步骤

最好的经验保留方式是让错误做法**没有出现的机会**。

```diff
- tar -xzf pkg.tar.gz -C dest --strip-components=2 pkg/data
- # ⚠️ 别用 2!会把 data/ 这层也剥掉,内容散进 dest/
+ # --strip-components=1 保留 data/ 这一层
+ tar -xzf pkg.tar.gz -C dest --strip-components=1 pkg/data
```

### 数值保留,依据压缩成一句

阈值、超时、md5、指纹必须留,但依据写成机制而不是故事。

```diff
- # 300 秒是按四台定的。六台同时从同一个 mount 读同一份权重,第六台没赶上,
- # 而一台超时会把已经起好的五台全部拆掉。改成 900。
+ # 900 秒:整池共用一个 blob mount,权重加载时间随台数线性增长,且任一台
+ # 超时会拆掉整池。
```

### 不要留清理的痕迹

删完就是删完。不写"(已简化)"、"(原注释见 git 历史)"、"(此处略)"。
git 记得,文档不必记得。

## 什么不要动

清理的对象是**会被当作现行指南来读**的东西:

- `README` / `SETUP` / 安装与运维文档
- 模块与函数 docstring
- 配置文件注释(`.env`、`*.yaml`)
- skill 与操作手册

**不要动本来就是档案的东西**——它们的用途就是记录当时发生了什么,删掉等于销毁记录:

- git commit message 和 git 历史
- 实验日志目录(`report/<date>-*/`、`refine-logs/`、周报、handoff)
- `CHANGELOG`
- 事故复盘/postmortem 文档
- 第三方 vendor 代码(`*/upstream/`)

边界不清时问用户,不要自己扩大范围。

## 执行方式

1. **先读项目级说明**(见 §0)。有约束就先解决冲突,再谈范围。
2. **先划范围再动手。** 列出要改的文件清单给用户确认,尤其当范围里混着档案类文件。
   若项目在版本控制里有多个分支,通常只清理**本分支已经与基线分叉的文件** ——
   清理未分叉的文件会凭空制造 diff 和合并冲突。
3. **一次一个文件,diff 要可读。** 大范围正则替换会误伤代码字符串和 vendor 代码。
4. **先搜信号词定位**,不要通读:

   ```bash
   rg -n "曾经|本来|原来|以前|之前是|后来|那次|事故|踩坑|注意|小心|警告|不要|别|否则|导致|坑" --type md --type py --type yaml
   rg -n "\b(20[0-9]{2}-[0-9]{2}-[0-9]{2}|once|used to|previously|历史原因|WARNING:|NOTE:|XXX|FIXME)"
   ```

5. **改完跑一遍测试。** docstring 会被 doctest 或断言引用,配置注释可能在 heredoc 里。
6. **报告时说清删了什么类别**,不要逐条罗列——用户要的是"清理过了",不是新的一份历史记录。

## 一个必须守住的例外

有极少数约束,**它的唯一防线就是那段解释**:代码看起来完全可以简化,只有那句
"为什么不能"拦着。这种地方按规则 3 改写后要保证**机制说得足够硬**,让读者
自己能推出"不能那么改",而不是只剩一句没有分量的祈使句。

判断方法:改写完后自问"一个不知情的人读完这句,会不会觉得可以优化掉它?"
会,就说明机制没写够,补上机制——而不是把事故叙事加回来。
