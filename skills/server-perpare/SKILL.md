# 服务器环境准备

每个原子任务单独维护一份准备脚本。脚本上传到目标服务器后，为该任务创建独立环境；脚本和依赖清单保存在所属项目中。

## 1. 确认原子任务

读取项目约定和实际程序入口，列出本次要运行的原子任务、已有准备脚本、目标环境目录与验证命令。任务边界不清楚时先与用户确认。

- 每个 benchmark 分别整理；例如 ACEBench、AppWorld、τ²、BFCL 各有自己的准备脚本和环境。
- 每个 method 分别整理；同一方法的数据生成、训练等入口若可独立运行，继续拆成原子任务。
- 独立运行的模型推理服务也作为一个原子任务。多个 benchmark 可以访问同一服务，各自保留独立环境。
- 相同入口和依赖下的模型参数、数据划分与重复轮次作为运行配置，复用该任务的准备脚本。

沿用项目已有目录约定。没有约定时采用 `server-prepare/<task>/prepare.sh`，依赖文件放在同目录，目标环境由脚本参数指定。

## 2. 优先复用脚本

先查项目已有的环境准备脚本，再查该任务的上游安装入口。核对它们覆盖的程序、依赖版本及目标服务器的系统、GPU、驱动和 CUDA 条件。

匹配时直接上传现有脚本及其依赖文件，在目标服务器为该任务创建环境并执行验证。重复准备同一任务时复用自己的环境；其他任务始终使用各自环境。

已有脚本需要适配时，先手动解决实际差异，再将成功步骤回写原脚本并重新验证。

## 3. 缺少脚本时，先手动配置

为该原子任务创建独立环境，按项目及上游设置安装依赖、准备代码和必要资源。使用该环境执行任务入口，获得符合任务要求的实际结果后，再整理准备脚本。

只把最终成功所需的步骤写入脚本。手动配置和脚本重放均遵循下文的版本、来源与编译约束。

配置遇到阻塞时明确记录未完成的步骤；手动配置成功才进入脚本整理阶段。

## 4. 整理可迁移脚本

脚本应满足：

- 一份脚本对应一个原子任务，使用明确的环境路径和该环境的解释器执行安装、验证与运行。
- 目标环境目录、代码和数据位置通过参数或环境变量传入；资源路径采用项目约定，服务器地址由上传命令指定。
- 配置任务所需的全部依赖；模型、数据与缓存可使用已有共享目录，解释器和依赖环境按任务隔离。
- 凭据通过项目现有方式在运行时提供。
- 任一步骤失败时返回非零状态；成功后输出环境路径及该任务的运行、验证命令。

脚本及其依赖文件作为一个可上传目录维护。尽量调用已有安装入口；各任务保持独立的准备入口和环境。

### 依赖版本、来源与编译

- 脚本直接指定已验证的 Python 和包的确切版本，或引用随附的固定版本依赖清单；传递依赖也固定为验证通过的版本。代码来源固定到具体 release 或 commit，预制环境、镜像使用明确版本。
- 包的指定版本在安装源中不可用时，在脚本中写明可用的下载来源和版本，例如 GitHub Release 的具体 wheel URL。GitHub 仓库来源需指定 URL 和 commit，并遵守下述编译限制。
- 依赖优先使用网上已有、适配目标 Python、CUDA 和系统的预编译 wheel、环境或镜像。
- 大型第三方库禁止在本机和远程训练节点自行编译。安装时显式禁用源码构建：pip 使用 `--only-binary=:all:`，其他安装器使用等效选项；下载 GitHub 源码同样受此限制。缺少兼容二进制时查找可用 wheel、预制环境或镜像。
- 小型运行时模块允许编译，单独列出并安装，保持其余依赖的源码构建禁用设置。

## 5. 重新运行并验证

将整理好的脚本及依赖文件上传到目标服务器，指定一个全新的环境目录，从头执行脚本。再用脚本创建的环境运行同一个验证任务，确认依赖安装、程序执行和结果输出均成功。

验证方式遵循项目约定和当前运行授权；项目要求直接跑正式实验时，用已授权的实际任务验证。保留手动配置与脚本重放各自的命令、环境路径和结果位置，日志放在所属模块的 `logs/` 下。

脚本重放或任务验证失败时，修正成功步骤并重新验证。只有脚本创建的环境通过实际运行验证，才将它作为该原子任务可复用的准备入口。

交付时简要列出各原子任务的脚本路径、环境路径、验证结果和未完成项。后续更换服务器，从复用这些脚本开始。
